# 02 · 创作管线流水线

> 定义主系统生成正文的完整流程：三层嵌套循环、章级十步管线、章后管线 A→B→C、回炉修订、幕/卷收尾。
> 版本：1.0 ｜ 依赖：`01` ｜ 相关：`03`(大纲)、`04/05`(真相)、`07`(审计)、`08`(提示词)

---

## 1. 三层嵌套循环

```
外层循环：卷
  └─ 中层循环：幕
       └─ 内层循环：章（十步管线）
```

每写完一章执行章级十步管线；每写一幕执行幕间文学质量报告；每写一卷执行真相文件全量校验 + 卷间文学质量报告。

## 2. 章级十步管线

每写一章必须执行的完整流程：

**① 规划**
- 展开当前章节的大纲节点（从四层大纲提取）
- 确认本章在卷纲/幕纲中的位置
- 检查 `reveal_density`，确定本章可揭示的设定量
- 从技能库读取适用技能（按题材、注入点、触发条件过滤）
- 激活技能时检查冲突矩阵：同分类同注入点的技能不能同时激活
- 同时激活上限 **5 个**；技能总 token 预算 **5000 tokens**

**② 生成**
- 组装提示词（五层结构，见 `08`）
- Layer1 系统级指令（叙事宪法、反AI味协议）｜ Layer2 上下文注入｜ Layer3 任务级指令｜ Layer4 技能注入｜ Layer5 审计注入
- 生成正文，流式输出。rules 不注入生成上下文，只注入审计层。

**③ 质控**
- 执行审计（见 `07`）。审计不通过 → ④ 回炉修订；通过 → ⑤ 收尾。

**④ 收尾**
- 若审计不通过：定位问题 → 修订正文 → 回 ③ 重新审计
- 若通过：执行技能规则审计；判断是否有 revision 注入点技能需执行修订建议

**⑤ 维护（章后管线，见下）**

## 3. 章后管线 A→B→C（DAG 依赖）

按 A→B→C 顺序执行，B 不能在 A 完成前执行。

**章后管线-A（创造性，LLM 驱动）** — 产出 `foreshadowing.md` 更新 + `chapters/ch_XXX_post_analysis.md`
- 伏笔规划：检测无意新伏笔 → 分类（authorized/candidate/noise）；推进已有伏笔状态（planted→progressing→converging→revealed→resolved）
- 语义演化链更新、读者预期分析、隐藏设定揭示记录

**章后管线-B（确定性，规则驱动）** — 产出 `characters.md`/`relations.md`/`factions.md`/`locations.md`/`timeline.md`
- 人物状态、关系变化（旧记录保留，新版本追加）、时间线推进、势力变动、地理更新
- 「精华借鉴」本章后管线-B 对真相文件的写入须符合 `05` 的记忆写入协议：记录**来源章节 + 生效时间 + 溯源**，而不是原地覆盖。

**章后管线-C（纯记录，零 LLM）** — 产出 `chapters/ch_XXX_summary.md` + 更新 `index.json`
- 章节摘要、时间戳、索引更新（角色/地点/伏笔引用）、合规检查（A→B→C 顺序，INV-008）

## 4. 幕间收尾

每写完一幕（通常 5-8 章）执行幕间文学质量报告（六维度，见 `11`）：
叙事节奏、角色弧光、伏笔推进、张力曲线、与卷纲对齐度。

## 5. 卷间收尾

每写完一卷（通常 3-5 幕）执行：
- 真相文件全量校验（跨文件一致，见 `11`）
- 卷间文学质量报告（叙事完整性、主题一致性、伏笔密度、角色发展）

## 6. 章节摘要格式

每章完成后由章后管线-C 生成摘要，存入 `chapters/ch_XXX_summary.md`。摘要是后续 Layer2 前情摘要注入和全量校验的数据源。

```markdown
# 第X章摘要
## 基本信息
- 章节类型：{战斗/对话/探索/日常/转折/文艺段落}
- POV：{视角角色}
- 字数：{实际字数}
- 故事内时间：{时间锚点}
## 剧情梗概（3-5句话）
## 关键事件（事件/角色/动作/后果）
## 角色状态变化
## 关系变化（驱动事件）
## 地点变化（状态变化）
## 伏笔操作（植入/推进/揭示 + 伏笔ID）
## 设定揭示（来源：隐藏设定[HS-XXX]）
## 未解决的悬念
## 章尾状态（角色/地点/状态 + 下一章钩子）
```

**摘要使用规则**：上下文注入只注入前 3-5 章摘要；全量校验遍历所有摘要做跨章一致；摘要由章后管线-C 生成后不可修改（除非用户在暂停状态下手动改）。

## 7. 回炉修订流程

```
审计结果
  ├─ 修复后通过（60-74分，Major 无 Blocker）→ 第1轮定向修订 → 重新审计 ③
  │     仍不通过 → 第2轮修订
  ├─ 回炉重写（<60 或有 Blocker）→ 保留章纲/节拍，全面重写 → 重新审计 ③
  │     仍不通过 → 第2轮重写
  └─ 达最大尝试次数（novel_meta.yaml 的 revision_max_attempts，默认3）
        → 升级：向用户报告问题清单+修订记录；建议手动介入；标记"需人工干预"
```

**修订策略**：修复后通过只改问题段（最小改动）；回炉重写保留章纲与节拍分解；每轮修订后执行完整审计；修订记录存 `audits/revision_ch_XXX.md`。

**升级触发**：① 连续 3 次不通过 ② 同一 Blocker 2 轮后仍在 ③ 修订后出现新 Blocker。

## 8. 编排实现建议

「精华借鉴」若用 LangGraph 编排本管线（参考 `langchain-ai/langgraph` 与 `Cppys/OpenNovel`）：
- 将"规划 → 生成 → 审计 → 回炉 → 章后管线A/B/C"建模为 DAG 状态机
- 每步写入 state 时叠加 Checkpoint，启用时间旅行与中断恢复
- 审计不通过时从"审计"节点回环到"生成"，天然表达回炉
- 用户暂停/复审映射为 Human-in-the-loop 的 interrupt / pause-resume
- 该编排层的状态快照即 `10` 中回滚机制的实现载体
