## 1. 三实体架构

整个创作系统由三个独立实体组成：

**小说创作主系统** — 核心创作引擎。通过 Pipeline 十步管线逐章生成小说内容，每一步有明确质量检查标准。主系统包含四层大纲、六系统真相文件、45 维审计层、提示词系统。主系统内 Agent 起**监控**作用，不直接改内容，发现问题后调用内置流程（修订、回炉）让内容达标。

**技能制造子系统** — 辅助用户创作自定义写作技能。用户决定造什么技能、技能怎么写、要不要入库。子系统的 Agent 只给建议，不决策。技能造好后写入技能库，等用户想用时被主系统读取。

**技能库** — 独立存储层。存技能 YAML 文件、冲突矩阵、版本快照。被子系统写入，被主系统读取。技能库本身不做逻辑，只做存储。

## 2. 单向数据流

```
子系统 ──写入──→ 技能库 ──读取──→ 主系统

主系统 ──×──→ 子系统     （无数据流）
主系统 ──×──→ 技能库写入  （主系统只读不写）
子系统 ──×──→ 主系统     （无数据流）
```

确保子系统永远不会影响主系统运行。主系统创作状态、质量数据、使用反馈不回流。若主系统发现某技能效果不好，由用户决定是否去子系统修改。

## 3. 设计原则

1. **三实体独立** — 主系统、子系统、技能库各自独立，技能库不隶属任何一方
2. **单向数据流** — 子系统写入技能库，主系统读取技能库，反向零数据流
3. **用户决策权** — 辅助用户造技能，入库/修改/删除由用户决定
4. **故障隔离** — 子系统出问题不影响主系统（主系统读技能库失败时降级为无技能模式）

## 6. 关键版本约束

- 引擎默认以"单章为最小提交单元"，完成后落到 `chapters/`。
- 所有真相文件写入走 `05` 的时效窗口/溯源机制，不做原地覆盖。
- 若实现层使用 LangGraph 编排，需要求每个节点的状态变更满足 `05` 的 Credentialed 记录，以支持回滚与审计。
